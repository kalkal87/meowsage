# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Meowsage is a small PySide6 (Qt) desktop app: a frameless, always-on-top pixel-art cat that floats over the desktop and reacts to the user's *own* recent coding activity, read from whichever of Claude Code (`~/.claude/projects/*/*.jsonl`) and Codex (`~/.codex/sessions/`) it finds installed. Higher recent activity → happier/more energetic cat; idle → sleepy cat. There is no packaging/build step — it's run directly as a Python module.

## Commands

```bash
# Setup (no venv is committed; .venv/ is gitignored)
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/pip install -e ".[dev]"   # adds pytest, for the tests below

# Run
./run.sh                      # exec's .venv/bin/python -m meowsage --foreground
python3 -m meowsage --foreground   # equivalent, if the venv is already active

# Run against fake/dev data instead of real Claude Code logs
MEOWSAGE_STUB=0.95 ./run.sh   # 0.0-1.0 activity level; drives StubUsageSource

# Tests
.venv/bin/pytest              # runs tests/
```

There is no linter or type-checker configured in this repo, and no CI. `tests/` covers the pure logic in `moods.py` and `usage.py` (mood-ladder cutoffs, percentile scoring, token weighting, log parsing) — everything that's plain data-in/data-out and doesn't need Qt or a real Claude Code/Codex install. It does not cover `animation.py`'s timer-driven state machine or `pet.py`'s `PetWindow`; verify those by running the app (headless smoke-testing via `QT_QPA_PLATFORM=offscreen` works well for exercising `Animator`/`PetWindow` logic without a real display — construct a `QApplication`, drive the relevant methods/timers directly, and call `.grab()` on the widget to force a real `paintEvent`).

Once the app is running, dev-only shortcuts/menu (only meaningful with `StubUsageSource`, no-ops on the real source):
- `Up` / `Down` — bump activity level by ±0.1
- `Q` — quit
- Right-click — context menu: force a mood, say something, wander now, quit
- Double-click the cat — poke (blink + speech)
- Drag — move the cat; the drop point becomes its new "home" for wandering

## Architecture

Data flows in one direction: **usage → mood → behavior → pose/render**.

```
usage.py (Usage/mood signal) → pet.py (PetWindow: polling + wiring) → animation.py (Animator: state machine + timers) → artwork.py (sprite lookup) → paintEvent
                                                        ↘ speech.py (SpeechBubble)
```

- **`usage.py`** — produces a `Usage` snapshot (`mood`, `activity_level`, `foreground_tokens`, baseline stats). Sources selected by `make_default_usage_source()` (honors `MEOWSAGE_STUB` and `MEOWSAGE_SOURCES` env vars):
  - `StubUsageSource` — manual activity level for dev/demo, driven by `bump()`/`set_activity()`.
  - `LogUsageSource` — scores one or more *readers* against their own recent history and reports whichever currently ranks busier (`mood_rank` in `moods.py`), so a Codex-only, Claude-only, or both-tools user all get one cat. Auto-detected from which log directories exist, or forced via `MEOWSAGE_SOURCES=claude,codex`. `ClaudeCodeUsageSource` is kept as a Claude-only alias for anyone importing it directly.
    - `ClaudeCodeReader` — parses assistant-message token usage out of `~/.claude/projects/*/*.jsonl`, weights tokens by type (`_CLAUDE_WEIGHTS`; output tokens count far more than cache reads). `_parse_claude_jsonl`'s cheap pre-filter (skip lines before bothering with `json.loads`) checks only for the quoted value `"assistant"`, not a specific key/colon/value spacing — an earlier, stricter version of that check depended on Claude Code's exact (space-free) JSON formatting and would have silently stopped counting activity if that ever changed; caught by `tests/test_usage.py`. If none of `_CLAUDE_USAGE_KEYS` show up in a message's `usage` object at all (a token field renamed upstream), it raises `ValueError` rather than silently scoring every message as zero activity — deliberately *not* caught anywhere upstream, so it surfaces instead of being swallowed. That means it would currently propagate out of `PetWindow._refresh_mood`'s 2s poll timer with no guard around it; see `tests/test_usage.py::test_claude_jsonl_raises_on_unrecognized_usage_shape`.
    - `CodexReader` — parses `~/.codex/sessions/YYYY/MM/DD/*.jsonl`. Prefers real per-category token usage when a session logs it (older Codex versions did); falls back to a flat per-turn weight otherwise — the current Codex release (0.147.0) logs no token usage at all, confirmed against both the rollout files and `state_*.sqlite`. See `docs/codex-support.md` for what that investigation found, including a `token_count` event whose `info` is `null` (a rate-limit-only ping) that must be skipped without resetting the running per-category diff.
  - Each source's events are bucketed and scored the same way: classify mood by comparing a recent "foreground" window (default last 60s, `PetConfig.foreground_window_seconds`) against a percentile of the user's own recent activity buckets over the last hour (`baseline_window_minutes`) — see `_classify_mood`/`_percentile_rank`. This is a relative, self-normalizing signal, not tied to any absolute token/plan limit, which is also why two tools never need to weight tokens comparably.
  - Tunables live in `config.py`'s `PetConfig`/`DEFAULT_CONFIG`. That module is deliberately import-free from the rest of the app so it can be loaded standalone.

- **`moods.py`** — `Mood` enum (`PLAYFUL > HAPPY > TRUSTING > CONTENT > RELAXED > TIRED > LOAFING > SLEEPY`, ordered by `_MOOD_RANK` in `animation.py`) and `mood_for_activity()`, the 0-1 → `Mood` cutoffs used by the stub path. Note the real sources (`ClaudeCodeReader`/`CodexReader`, via `LogUsageSource`) do *not* use those cutoffs — they map percentiles straight to `Mood`, so a new mood needs adding in both places. The v1 plan's full ladder has landed; Hunting also shipped, as an interrupt rather than a rung (see `docs/`). Also holds the flavor-text pools (`MOOD_LINES`, `PERK_LINES`) shown in the speech bubble.
  - **Naming landmine**: mood semantics were inverted from an earlier version of this app (`mood_for_usage` → `mood_for_activity`). High activity now means *happy*, not sleepy. If you see anchor/threshold values that look backwards, check which semantic you're in.

- **`pet.py`** (`PetWindow`) — the top-level `QWidget`. Polls `usage_source.get()` on a 2s `QTimer` (`_refresh_mood`), forwards mood changes into the `Animator`, and separately edge-detects activity resuming from idle (`_maybe_perk_up`, cooldown-gated) to trigger an immediate reaction rather than waiting for the next poll. Owns the `SpeechBubble` and a second independent ~12-25s timer for idle chatter. `paintEvent` reads `Animator.current_render()` each frame and does a single combined transform (flip for facing direction + squash/stretch scale, anchored at the sprite's feet) before drawing the pixmap — when scale is 1 and facing right, this transform reduces to a plain draw at `(cx, cy)`.

- **`animation.py`** (`Animator`) — owns *all* motion/pose state behind a set of `QTimer`s (pose choice every 6s, blink every 3-6s, breathing bob, walk-cycle frames, one-shot yawn/stretch/perk animations, cursor-gaze checks). `PetWindow` treats it as a black box: hook `update_needed`/`move_to` signals, call `current_render()` each paint. Behavior selection is weighted-random per `Mood` (`_POSE_WEIGHTS`); `Behavior` (what the cat is doing) is a coarser category than `Pose` (which literal sprite/frame). One-shot animations (yawn, squash-and-stretch, perk-up bounce) are time-elapsed-based (sampled from `time.monotonic()` inside `current_render()`), not frame-counted, and can chain (e.g. waking from sleep plays yawn → stretch → idle standing via the `then_stretch` flag). The Trusting flop is the exception and the one multi-frame chain: `_play_trusting_roll` cycles `_ROLL_CYCLE` on a frame timer, lands in `Behavior.TRUSTING_BACK` for a *randomly* long hold (every other one-shot here is a fixed duration), then settles into sitting. `TRUSTING_ROLL`/`TRUSTING_BACK` are only ever set while that chain's timers are running — `_tick_pose` refuses to re-roll out of them, so `_stop_trusting` resets the behavior to keep that invariant. The Playful zoomies is the same chain shape again, driving the walk's own target-and-step machinery with a bigger step and a faster tick over several dashes (`_play_zoomies`/`_next_zoomies_leg`/`_run_step`); `ZOOMIES` holds the same "only set while its timers run" invariant. Note `_walk_target` is shared by walking and zoomies — only one can be active at a time — and both step functions must treat "asked the window to move and it didn't" as arrival, since `PetWindow._move_within_screen` clamps to the screen and an unreachable target would otherwise loop forever. Hunting is the exception to all of the above: it is an *overlay*, not a rung — a `_is_hunting` flag (not a `Behavior`, not a row in `_POSE_WEIGHTS`) driven by a cursor-dwell tracker (`_check_stalk`, `STALK_*` constants), which overrides the pose for a few seconds and hands it straight back, so the ladder behavior underneath is never saved or restored. Note it disarms after each hunt and requires the cursor to move before re-arming — without that it would stalk an abandoned pointer forever. Procedural animations (stretch, perk bounce, cursor gaze) intentionally reuse the existing sprites rather than requiring new art — squash/stretch is a `QPainter.scale()` on the standing sprite, not a separate asset.

- **`artwork.py`** — `Pose` enum → sprite file mapping (`_POSE_FILES`), all backed by the PNGs in `meowsage/assets/`. Loads/caches per `(Pose, Mood)` pair, strips near-white backgrounds to transparency, and applies a light per-mood color tint (`_MOOD_TINTS`). Two gotchas when adding art: any pixel with all RGB channels above `WHITE_THRESHOLD` (240) is stripped to transparent, so near-white detail *inside* the sprite (eye whites especially) gets punched into holes unless darkened first; and sprites are scaled to `TARGET_WIDTH` then anchored at the pixmap's bottom edge in `paintEvent`, so a new pose must share the existing canvas size and ground line or the cat visibly jumps when it swaps in. Adding a new `Behavior`/animation that needs a genuinely new sprite (not just a procedural transform of an existing one) means adding both a PNG here and a `Pose` entry.

- **`speech.py`** (`SpeechBubble`) — an independent top-level, click-through, non-activating overlay window (not a child widget) that repositions itself above the pet's geometry. Deliberately avoids `raise_()`/focus-stealing on macOS.

- **`app.py`** — entry point; creates the `QApplication` and `PetWindow`, places it in the bottom-right of the screen's available geometry, and starts the event loop. Sets the Qt application name, which is *not* what the Dock and Cmd-Tab switcher display.

- **`appbundle.py`** — builds `~/Applications/Meowsage.app` for `meow install-app`, which is the only thing that makes macOS call the app Meowsage. Read its docstring before touching it: the design is dictated by three findings that are not guessable, all established by testing. (1) A shell script as `CFBundleExecutable` is refused outright by modern macOS — LaunchServices error -10669 — so a C stub is compiled with `clang`. (2) macOS names the app after the executable that ends up running, not after `CFBundleName`, so exec'ing the venv's `python` yields an app called "Python". (3) A framework CPython re-execs itself through the framework's own `Python.app`, which is a bundle in its own right and steals the identity — this is why the same code passed against Xcode's 3.9 and failed against Homebrew's 3.14. The fix is to copy the framework's `Python.app` binary into our bundle *named* `Meowsage` and exec that, with `__PYVENV_LAUNCHER__` set both to suppress the second re-exec and to point the interpreter at its venv. `CFBundleExecutable` is therefore `launcher`, not `Meowsage`: the app name is the interpreter copy's filename. Setting `QApplication.setApplicationName`/`setApplicationDisplayName`, patching `CFBundleName` through the ObjC runtime, passing `argv[0]`, and exec'ing via a renamed interpreter symlink were each tried and none of them move the label.

- **`cli.py` / `runtime.py`** — `meow` backgrounds itself so it doesn't hold the terminal: `_launch` runs the first-run naming prompt in the parent (while a tty is still attached), then re-enters via `sys.executable -m meowsage --foreground` under `start_new_session=True`, records the child in a pid file, and returns. **The gate is `_should_detach()`, and it must stay a tty check.** Launched from the `.app` bundle or the LaunchAgent there is no terminal, and detaching there would be actively wrong — the bundle's process *is* the app to macOS, so exiting immediately drops the Dock name that `appbundle.py` exists to provide, and launchd would see the job die. A tty distinguishes the two without needing a flag threaded through bundles built by older versions. `runtime.py` owns the pid file; `running_pid()` always confirms against `ps` before believing it, because SIGTERM skips the `finally` that would clear it (so stale files are normal and must never be trusted into killing a reused pid). `meow status` deliberately reaches for `make_default_usage_source()` (reporting which readers it picked in its `sources` row, via `LogUsageSource.readers`) and the bundle path *without* importing Qt — that's why `appbundle.py` imports `artwork` lazily inside `_build_icns`, and why status answers in ~50ms. `_offer_app_install` fires only when the naming wizard actually ran (first run *with* a terminal), since that is the one moment both a prompt and the user's attention are available; every failure path in it falls through to a running pet, because a Dock label is worth less than a cat.

- **`profile.py`** — `load_or_run_setup()` must never block on a question it cannot ask. Launched from the app bundle or at login there is no stdin, and the naming `input()` used to raise `EOFError` and kill the process before any window appeared — a silent no-op on double-click, which is the most natural way for a non-technical user to start it. `can_prompt()` (a tty check, same signal as `cli._should_detach`) gates the wizard, and the fallback `Profile()` is deliberately **not saved**: leaving the file absent means a later launch from a terminal still gets asked, rather than one double-click permanently committing the user to the default. `PetWindow.greet` reads the same absence to decide whether the hello carries the `meow rename` hint.

- **`banner.py`** — the ASCII logo `cli._launch` prints before importing `app` (that import pulls in PySide6, which is slow enough to look like a hang with nothing on screen). Pure ASCII and centred on the widest line in the whole banner, tagline included. `render()` returns a string so it can be checked without capturing stdout; colour is suppressed when stdout isn't a TTY, which keeps escape codes out of the LaunchAgent's log file.

- **Renamed from "Usage Pet"** — the package, dist name, `MEOWSAGE_STUB` env var, profile directory and LaunchAgent label all changed. Two migrations carry old installs over and are the only reason the old names still appear anywhere: `profile._migrate_legacy_profile` adopts `~/Library/Application Support/usage-pet/profile.json` on first launch (copying, not moving, so a rollback still finds it), and `cli._remove_legacy_agent` clears the `com.usagepet.meow` LaunchAgent so enabling autostart post-rename doesn't leave two agents running.
